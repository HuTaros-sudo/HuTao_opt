# 聖啓の塵：仕様調査メモ

調査日：2026-09-13（日本時間）  
対象：2026年9月13日までに公開され、今回アクセスできた情報。9月後半の更新は対象外。  
状態：基本ルールは確認済み。実ゲームの厳密な確率モデルは未確定。確率モデルを明示的な仮定として選ぶ計算層を実装済み。

## 1. 結論と情報の扱い

聖啓の塵は、所持聖遺物の追加ステータスの**強化配分をやり直す**仕組みである。新しい聖遺物を作る祈聖のエリクシルとは分けて扱う。基本操作は公式記事で確認できたが、抽選確率の全容は確認できていない。[O1](https://www.hoyolab.com/article/39387781)

以下のラベルを使う。

| ラベル | 意味 |
| --- | --- |
| 公式確認 | 公式アカウントの本文・説明画像で直接確認した内容 |
| 資料確認 | Wiki等の本文に記載がある内容。公式による直接確認や独立した実測検証とは区別する |
| 実装確認 | 固定コミットのコードで確認した挙動。実ゲームの正しさを保証するものではない |
| 仮定・導出 | モデル上の仮定、または明示した前提からの数学的結論 |
| 未解決 | 今回の資料では確定できなかった内容 |

情報源の優先順位は、①公式、②原神Wiki・KQM等、③GitHubの既存実装、④Redditなどの補助情報とする。HoYoLABは一般ユーザーも投稿できるため、ドメインだけで公式とは判定しない。Wikiのコメント欄も検証済み本文とは区別する。

## 2. 基本ルール

### 2.1 公式記事で確認できた事項

次の表は、原神公式の2025-06-18公開記事にある後半の聖啓の塵の説明画像を、ブラウザーで直接読んで確認したもの。[O1](https://www.hoyolab.com/article/39387781)

| 項目 | 公式確認した仕様 |
| --- | --- |
| 対象 | 最大レベルの★5聖遺物 |
| 再配分対象 | 追加ステータスの強化回数。ステータスの種類は変わらない |
| 選択 | 優先したい追加ステータスを2種類選ぶ |
| 通常再構築 | 選択したステータスに最低2回の強化を保証 |
| 結果の採否 | 再構築結果を見てから元の状態を保持するか、新しい結果を採用するか選べる |
| 消費数 | 花・羽：1個。砂・杯・冠：2個 |
| 聖言解明 | 塵1個の消費につき進捗1 |
| 上級再構築 | 進捗6で発動し、最低3回を保証 |
| 絶対再構築 | 上級を2回発動した後、次の上級が絶対に変わり、最低4回を保証 |

この保証はDamageの改善保証ではない。ステータスの配分とDamageの関係は、別の評価関数で判定する必要がある（本ツールの設計上の解釈）。

種類の維持は公式確認済みだが、**初期値と各強化の増加量の扱いは別の論点**である。

## 3. 確率モデル：確認できた既存実装

### 3.1 調査対象

Genshin Optimizerのコミット`180a0a1015cb725c7570cd828eb086749960df98`を参照した。GitHub APIで確認したコミット日時は2026-08-27で、調査の対象期間内。コードは読んだが、実行・移植・ゲームとの比較実験はしていない。

### 3.2 強化先の分布

`rollCountProb`は、通常時の強化先を4種類均等として計算し、選択した2種類への合計回数が保証未満になる確率を、保証回数ちょうどの結果へ集約する。保証を超える回数の確率は通常時のまま。**これは実装確認であり、公式確率ではない。** [G2](https://github.com/frzyc/genshin-optimizer/blob/180a0a1015cb725c7570cd828eb086749960df98/libs/gi/upopt/src/markov-tree/mathUtil.ts)

この実装の合計回数分布は、次のように表現できる（コードからの数学的導出）。

- `N`：再配分する強化回数。
- `g`：保証回数（2、3、4）。
- `X ~ Binomial(N, 1/2)`。
- 選択した2種類への合計強化回数`K = max(X, g)`。

選択した組の内部では2種類へ均等に配分し、非選択の組でも同様に配分するモデルである。前提は`N >= g`、4種類中2種類を選択すること。[G2](https://github.com/frzyc/genshin-optimizer/blob/180a0a1015cb725c7570cd828eb086749960df98/libs/gi/upopt/src/markov-tree/mathUtil.ts)

例：**このモデルに限って**`N=5`の場合は次の分布になる。これはゲーム内の実測表ではない。

| 保証g | K=2 | K=3 | K=4 | K=5 |
| --- | ---: | ---: | ---: | ---: |
| 2 | 50% | 31.25% | 15.625% | 3.125% |
| 3 | 0% | 81.25% | 15.625% | 3.125% |
| 4 | 0% | 0% | 96.875% | 3.125% |

同じ「最低g回保証」でも、次の方式は異なる分布になる。

- 最初からg回を選択組へ配り、残りを無条件抽選する。
- 全回抽選し、保証未満なら全体を引き直す。
- 必要な分だけ補正し、保証未満の確率を保証値へ集約する。

保証文言だけからどれかを決定できない。上表を実ゲームの確率として使うには、追加の検証根拠が必要。

### 3.3 ロール値と初期3・4オプション

GOの`expandRollsLevel`は、増加量を最大値の70%・80%・90%・100%という4段階の等確率・独立な抽選として扱う。`expandSubstat.ts`の平均・分散も同じモデルに基づく。[G3](https://github.com/frzyc/genshin-optimizer/blob/180a0a1015cb725c7570cd828eb086749960df98/libs/gi/upopt/src/expandRolls.ts)、[G4](https://github.com/frzyc/genshin-optimizer/blob/180a0a1015cb725c7570cd828eb086749960df98/libs/gi/upopt/src/expandSubstat.ts)

一般の聖遺物では、4種類がそろうまでの追加と、その後の強化を区別する必要がある。KQMのガイドは初期3種類なら+4で4種類目を獲得する一般ルールを説明しているが、ガイドの対象はVer.4.6であり、塵の直接的な検証資料としては使えない。[K1](https://keqingmains.com/misc/artifacts/)

塵への適用については、GOは総ロール数から4種類分を引いて再配分回数を求める。したがって総ロール数8なら4回、9なら5回になる。総ロール数不明時のフォールバックまで自作ツールで無条件に踏襲しない。[G1](https://github.com/frzyc/genshin-optimizer/blob/180a0a1015cb725c7570cd828eb086749960df98/libs/gi/upopt/src/upOpt.ts)

また、初期値入力に関するGOのPRには、表示丸めとロール分解の曖昧さが報告されている。初期値を現在値から勝手に確定するのは避ける。[G5](https://github.com/frzyc/genshin-optimizer/pull/3269)

### 現在のプロジェクト実装

`src/genshin_opt/dust.py`は、強化先について`go_capped_binomial`を明示指定した場合だけ結果分布を計算する。ロール増加量とその確率は組み込まず、呼び出し側が4種類すべてについて渡す。結果には強化先モデル、ロール値モデルID、抽選条件を残す。

この実装は上記の既存実装モデルを再現するためのもので、U1〜U3を解決したり実ゲームとの一致を保証したりするものではない。更新確率と期待値の計算は任意の評価関数を受け取り、optimizerやAkashaから独立している。

## 6. 将来の実装に必要なデータと指標（設計上の提案）

ここからはゲーム仕様ではなく、このプロジェクトの設計案。

### 入力として残すデータ

- 聖遺物ID、部位、セット、レアリティ、レベル、メインステータス。
- サブステータス4種類の現在値と初期値。初期値が不明なら明示的に不明とする。
- 初期3種類／4種類、または再配分可能な強化回数。その情報の取得元。
- エリクシル産かどうか、作成時の指定2種類。
- 今回指定する2種類、塵所持数、現在の進捗と保証段階。
- 使用する確率モデルのID、根拠、対象時点、未解決項目。

初期値不明の場合は、厳密計算を保留するか、可能な初期値ごとの結果範囲を出す。候補間を等確率とすることも追加仮定なので、黙って平均しない。

### 「更新」と「期待値」の定義

他の4部位を固定し、同じ評価条件で比較する。元の評価値を`S0`、再構築候補を`S`とすると、次を分けて表示する。

| 指標 | 定義 |
| --- | --- |
| 更新確率 | `P(S > S0)`。同点は更新に含めない |
| 候補の期待値 | `E[S]` |
| 良い方を保持した後の期待値 | `E[max(S0, S)]` |
| 保持後の期待改善量 | `E[max(0, S - S0)]` |
| 更新時の平均改善量 | `E[S - S0 | S > S0]`。更新確率0なら未定義 |

元の状態を保持できるため、実際の採用判断を表す期待改善量は負にならない。ただし塵は消費される。塵1個あたりの効率は改善量を消費個数で割るが、将来の保証段階の価値まではこの比率に含まれない。

Akashaとの接続は不要。人工的な評価関数・確率分布で、確率の総和、保証下限、期待値、元を保持する処理を独立テストできる。GOモデルを採用する場合の上表はモデル内テスト用であり、実ゲームとの一致を検証するテストとは分ける。
